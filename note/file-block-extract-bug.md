# AI Agent 项目：Markdown 代码块提取不完整的 Bug 排查

## 问题现象

运行 `demo-search.ts`（搜索 → 大模型生成学习笔记 → 写入本地文件）时，`output/` 目录下生成的 markdown 文件内容**不完整**：文件只写到「步骤1：环境与依赖准备」就结束了，后面的步骤 2/3/4 和注意事项全部丢失。

但从流式输出的完整内容看，模型实际上生成了完整的笔记（包含 4 个步骤 + 4 条注意事项）。

## 错误排查过程

### 第一步：排除模型输出截断

一开始怀疑是 `max_tokens` 设得太小（默认 4096），导致模型生成到一半被强制截断。调大 `max_tokens` 后问题依旧。

进一步查看流式输出的完整 `fullContent`，发现模型完整输出了所有内容，说明**不是模型生成的问题，而是提取逻辑的问题**。

### 第二步：定位正则匹配 Bug

写文件的逻辑在 `processFileOperations` 方法里，核心正则是：

```js
/```(?:filename:|file:)([^\n]+)\n([\s\S]*?)```/g
```

注意 `[\s\S]*?` 是**惰性匹配**——从开头往后找，遇到第一个 ` ``` ` 就停止匹配。

再看模型生成的笔记内容，里面有嵌套的代码块：

```markdown
```filename:deep-agent-notes.md
# 学习笔记

### 步骤1：环境与依赖准备
```bash
pip install langchain deepagents
```
> 框架默认使用 xxx 模型。

### 步骤2：初始化...
```

笔记里的 ```bash ... ``` 是嵌套代码块。正则匹配到 `pip install` 下面的 ` ``` ` 就认为结束了，**后面的步骤 2/3/4 和注意事项全部被丢弃**。

### 第三步：复现验证

构造了一段包含嵌套 bash / python 代码块的完整 AI 回复，用原正则测试：
- 原正则提取的内容：只到「步骤1」就结束，长度 233 字符
- 预期内容：包含 4 个步骤 + 4 条注意事项，长度 700+ 字符

确认 Bug 复现。

## 解决方案

### 方案对比

| 方案 | 思路 | 缺点 |
|---|---|---|
| 改贪婪匹配 `[\s\S]*` | 匹配到最后一个 ``` | 一段回复里有多个 filename 代码块时会跨块吞内容 |
| 从后往前找最后一个 ``` | 假设只有一个文件 | 不支持多文件场景 |
| 行扫描 + 围栏计数 | 逐行解析，维护嵌套深度 | 实现稍复杂，但最严谨 |

选了**行扫描 + 围栏计数**的方案，和 Markdown 解析器的标准做法一致。

### 实现思路（`extractFileBlocks` 方法）

```
遍历每一行：
  遇到 ```filename:xxx  → 开围栏，fenceDepth = 1，开始收集内容
  遇到 ```xxx（非空）  → 内部代码块开始，fenceDepth++，计入内容
  遇到 ```（空行/纯反引号）→ fenceDepth--
    fenceDepth == 0  → 当前文件块结束，存入结果
    fenceDepth > 0   → 内部代码块结束，仍计入内容
```

### 防御性处理

- 如果 AI 回复被截断（没有闭合的 ```），也把已有的内容算进去，不会因为没写完就完全丢失
- 支持多文件（多个 ```filename 块）

## 验证

用包含 2 层嵌套（bash、python）、4 个步骤、4 条注意事项的完整回复测试：

| | 原正则 | 修复后 |
|---|---|---|
| 内容长度 | 233 字符（仅步骤1） | 700+ 字符（完整） |
| 包含步骤 2/3/4 | ❌ | ✅ |
| 包含注意事项 | ❌ | ✅ |
| 嵌套代码块保留 | ❌（被吞掉） | ✅（完整保留） |

类型检查通过，单元测试 13/13 通过。

## 面试版本：遇到过什么问题 + 怎么排查的

> 面试官：做当前项目的时候遇到过什么印象深的问题吗，怎么排查和解决的？

我做 AI Agent 项目的时候遇到过一个很典型的「看起来简单但容易踩坑」的问题。

**背景**：项目里有个功能，让大模型生成 Markdown 笔记，然后通过约定的 ` ```filename:xxx.md ` 格式把内容提取出来写入文件。

**现象**：生成的笔记文件总是不完整，只写到一半就没了。

**排查过程**：

第一步我先怀疑是 `max_tokens` 太小导致模型输出被截断，调大之后问题依旧。然后我打了个日志，把模型完整输出（流式拼接后的 fullContent）打出来看——发现模型实际上生成了完整内容，那问题就不在模型侧，而是**内容提取这一步出了问题**。

顺着调用链找到了提取文件的正则。我一眼看到正则用的是惰性匹配 `[\s\S]*?`，就猜到原因了——惰性匹配遇到第一个 ` ``` ` 就停了，但模型生成的笔记里**嵌套了 bash/python 代码块**，这些嵌套代码块的结束反引号被当成了外层文件代码块的结束标记。

为了确认，我写了个最小复现：构造一段含嵌套代码块的内容丢给正则，果然只提取到第一个嵌套代码块之前的内容。

**解决方案**：我没有简单把惰性改成贪婪——贪婪在多文件场景下会跨文件吞内容。最终用了**行扫描 + 围栏计数**的思路，类似 Markdown 解析器的做法：遇到 ` ```filename ` 开一层，遇到内部 ` ```python ` 再加一层，遇到纯 ` ``` ` 减一层，只有回到 0 才算一个文件块结束。这样不管嵌套多少层都能正确识别边界。

顺便还加了一个防御：如果模型输出被截断（没有闭合的 ```），也把已有的内容写入文件，不会完全丢。

**我从这个问题里学到的**：

1. **对 LLM 输出做结构化提取时，不能假设输出格式"一定很简单"**——大模型的输出是开放的，代码里嵌代码这种嵌套情况经常发生，正则要考虑嵌套、要考虑不完整的情况。
2. **排查问题要分层定位**：先确定是模型的问题还是我代码的问题（打 fullContent 日志一步就排除了模型侧），再逐步缩小范围。一开始我盯着 max_tokens 调了半天，其实根本不在那个方向上。
3. **看似简单的需求（"从文本里提取代码块"）真的写对也不容易**，边界情况往往比主逻辑更重要。
